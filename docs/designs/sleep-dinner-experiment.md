# Design: Late dinner vs. deep sleep (n=1 experiment on the health MCP)

## Problem Statement

I wear a Fitbit Air and want to talk to my own health data from an AI chat. Logging meals by conversation or photo into Google Health is the input side. The payoff is answering a real question about my own body with evidence instead of generic advice. The first question: **does eating dinner late reduce my deep sleep?**

This builds on the thin Google Health MCP (layer 1, OpenSpec change `add-health-mcp-core`). The experiment is the first layer-2 package.

## What Makes This Cool

- It joins two data streams that none of the apps I use join under a controlled schedule: when I ate (my meal log) and how I slept (Fitbit sleep stages).
- The AI runs a real experiment for me: it assigns early and late dinner nights, tracks whether I followed the plan, and at the end reads out a number computed in code. An illustrative readout (not an expected result): "late-dinner nights: 18 minutes less deep sleep (95% CI 6 to 30)", or "no clear effect", or "not enough data".
- My body becomes the lab; the same machinery later runs other questions (caffeine to HRV, hydration to resting heart rate).

## Constraints

- Owner plus a few testers; Google OAuth app in Testing mode (weekly re-login).
- Layer 1 MCP stays a thin API mapping; no domain logic there.
- Fitbit Air is screenless and cannot receive third-party vibrations; reminders go to the phone.
- Health data of testers is sensitive: store the minimum, no health values in logs or in experiment state.

## Premises

1. Meal logging must take at most ~30 seconds (one photo or one sentence), or the experiment has no data.
2. Experiment logic (schedule, comparison, verdict) lives in layer 2; the thin MCP only supplies data.
3. The result must be honest: the readout never claims an effect or "no effect" that the numbers do not support.
4. Control nights are required: the experiment assigns which evenings are early and which are late.

## Approaches Considered

- **A. Skill only.** Rejected: the model compares two weeks of sleep "by eye" and will likely find a pattern that is not there (violates premise 3); state is lost between conversations.
- **C. Calendar as the experiment UI.** Not chosen for v1: free phone reminders, but adds a Calendar scope and does not solve analysis. Possible later add-on.
- **B. Experiment module with deterministic statistics.** Chosen (below).

## Recommended Approach

**B: an experiment module ("lab") with statistics computed in code, and a conversational skill on top.**

### Placement and auth
- The lab tools are a separate tool group (`lab_*`) in the **same MCP server and Cloud Run service** as layer 1, so testers connect one connector and sign in once.
- The layer-1 boundary is kept in code: the lab module calls the layer-1 Google Health client (the same functions behind `read_data`), never the other way round. Layer-1 tools contain no experiment logic.
- The lab uses the signed-in user's Google credentials through layer 1. When Google access has expired (weekly in Testing mode), lab tools return the same reconnect error and link as layer 1. Experiment state lives in Firestore and is unaffected by re-login. The layer-1 spike confirms that data from before the re-consent stays readable.

### Tools
One active experiment per user at a time. "Today" and "tonight" are always in the user's time zone from their Google Health profile.

| Tool | Behavior |
|---|---|
| `lab_create_experiment(template="late_dinner_sleep", start_date, planned_bedtime?)` | Creates the protocol and schedule. `planned_bedtime` defaults to the median sleep onset of the last 14 nights. Fails if an experiment is already active. |
| `lab_today()` | Tonight's arm and a concrete cutoff: early = "finish all eating by {planned_bedtime - 3.5 h}", late = "eat dinner between {planned_bedtime - 2 h} and {planned_bedtime - 1 h}". Returns "no active experiment" or "experiment finished, run the analysis" when relevant. |
| `lab_flag_night(date, code)` | Marks a night as disturbed (code `user_flag`) or skipped (code `skipped`). See flag rules. |
| `lab_status()` | Nights done, valid pairs so far, exclusions by code, adherence, and a warning when the run is projected to end below the minimum. |
| `lab_analyze()` | The verdict and numbers (see Analysis). |

### Schedule
- Nights are grouped into **pairs of consecutive nights**; each pair has one early and one late night in random order (seeded; the seed is stored with the protocol).
- Weekend nights are Friday and Saturday. Pairs are aligned so that Friday and Saturday always form one pair, so both arms get the same number of weekend nights for any `start_date`. If alignment leaves a single night at the start, it is a run-in night: assigned "early", not analyzed.
- Default length: 7 pairs (14 nights). If fewer than 5 valid pairs exist on the last scheduled night, the schedule auto-extends by one pair at a time, up to 14 pairs (28 nights), then stops with whatever verdict the data supports.

### Definitions
- **Experiment night:** local noon to the next local noon.
- **Main sleep:** the longest sleep session starting within the experiment night and lasting at least 3 hours; naps and shorter sessions are ignored.
- **Sleep onset:** the session's sleep-onset time if the Google Health API exposes it; otherwise the session start (time in bed). The readout states which source was used. Thresholds are the same in both cases.
- **Last intake:** the latest nutrition-log entry of the experiment night with an eaten-at time between 15:00 and sleep onset that is food, a caloric drink (over 50 kcal) or alcohol. Water and zero-calorie drinks do not count.
- **Eaten-at time:** the time the food was eaten, which may differ from when it was logged. When the user logs a meal more than 20 minutes after "now" might apply (photo later, "I had..."), the skill asks when it was eaten. The layer-1 spike verifies that nutrition entries carry an editable time.
- **Adherent night:** early if last intake was at least 3.5 h before sleep onset; late if 2 h or less; anything else is non-adherent.

### Exclusions
Stored as codes only: `no_dinner_logged`, `no_sleep_data` (tracker not worn, battery, no stage data), `travel` (time zone changed by more than 1 hour), `user_flag`, `skipped`. A pair with any excluded night is not a valid pair.

Flag rules: a flag or skip counts as an exclusion only if it was recorded before the main sleep session of that night ended. Later flags are listed in the readout as "flagged after the fact" and do not exclude the night.

### Analysis
- **Primary outcome:** deep-sleep minutes of the main sleep. It alone drives the verdict.
- **Primary analysis (by assignment):** for each valid pair, difference = deep minutes (late night) minus deep minutes (early night). Report the mean difference with a paired t-interval (95%, df = pairs - 1). Deterministic: no resampling, no randomness in the analysis.
- **Secondary analysis (per protocol):** the same, restricted to pairs where both nights were adherent. Reported descriptively, no verdict of its own.
- **Secondary outcomes:** deep-sleep %, total sleep, overnight HRV: mean differences only, labeled descriptive, no verdict.
- **Verdicts and exact wording the skill must use:**
  - `not_enough_data` (fewer than 5 valid pairs): "Not enough data to say anything yet." No CI shown.
  - `effect` (CI excludes zero): "Late-dinner nights had X minutes {less|more} deep sleep on average (95% CI A to B)."
  - `no_clear_effect` (CI includes zero): "No clear difference in deep sleep between early and late dinners in this experiment (95% CI A to B). This does not show there is no effect."
- **Stated limitation in every readout:** consecutive nights are not fully independent (sleep debt carries over). Pairing adjacent nights reduces but does not remove this.

### Thresholds (tunable v1 defaults stored in the protocol)
- 3.5 h early / 2 h late: common guidance separates "finished 3+ hours before bed" from "eating close to bed"; the gap between them keeps the arms distinct.
- 5 valid pairs minimum: below that a paired t-interval is too wide to be useful.
- 7 to 14 pairs: two weeks is a tolerable commitment; four weeks is the cap before the experiment becomes a lifestyle.

### State (Firestore `users/{id}/experiments/{expId}`)
Template, start date, planned bedtime, thresholds, seed, schedule (date to arm), status, and per-night flags as `{date, code, recordedAt}`. No free-text reasons, no meal contents, no sleep values, no derived gaps. Health values are re-read from Google Health at analysis time.

### Skill
Runs the conversation: start (with a short "this is not medical advice; skip any night that doesn't suit you, and don't do this if late eating is a problem for you, e.g. reflux or diabetes" notice), the morning "what's tonight?", quick meal logging with eaten-at time, flags and skips, and the final readout. It always quotes `lab_analyze` wording and numbers verbatim, never its own estimate.

## Open Questions

- Whether the daily "tonight: early/late" nudge rides on the future push-reminder package, or asking the AI in the morning is enough for v1.

## Success Criteria

- I log every evening intake (dinner and anything after it) for the whole run, each log in 30 seconds or less.
- At the end, `lab_analyze` returns one of the three defined verdicts, with a CI whenever there are at least 5 valid pairs, and the AI's answer quotes that wording and those numbers exactly.
- A tester can run the same experiment on their own data without seeing mine.

## Distribution Plan

Web service: part of the same Cloud Run MCP server as layer 1; testers connect one custom connector in Claude. The skill ships in this repo (and as a copyable Claude skill for testers).

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — feasibility

**Problem**

> The schedule cannot work as written. A week has 7 nights, so if Friday and Saturday always form one pair and every other night is paired with its consecutive neighbor, one night per week has no partner (with Sun-Mon and Tue-Wed pairs, Thursday is left over every week). The document handles only a single leftover night at the start ('run-in night'), so a 7-pair run of consecutive nights is impossible for any start_date, and '7 pairs (14 nights)' cannot hold.

**Remedy**

> Define the pairing over a full week: e.g. pairs Sat-Sun or Fri-Sat plus a fixed weekly unpaired night (assigned, not analyzed), or non-adjacent pairs within a week. State how many calendar nights a 7-pair run takes, and add a fixture test that checks every night for every start weekday.

### R2-2 — consistency

**Problem**

> The primary analysis is called 'by assignment', but a pair with any excluded night is dropped, and the exclusions include `no_dinner_logged`. Whether dinner was logged is post-randomization behavior tied to adherence (e.g. logging lapses on social late-eating nights), so dropping those pairs from the primary analysis brings back the selection that intention-to-treat was chosen to avoid. The outcome (deep sleep) does not need a meal log.

**Remedy**

> Separate the exclusions by analysis: the primary by-assignment analysis excludes only nights with missing outcome, travel, and pre-registered flags or skips; `no_dinner_logged` only removes a pair from the per-protocol analysis (adherence unknown). Update the valid-pair count used by the minimum and the auto-extension to match.

### R2-3 — consistency

**Problem**

> Main sleep must last at least 3 hours, and a night without main sleep presumably becomes `no_sleep_data`. The outcome can drive that exclusion: if a late dinner causes badly fragmented or short sleep (sessions under 3 h), the night that shows the harm is dropped. This biases toward 'no clear effect' and conflicts with premise 3.

**Remedy**

> Define how a night whose sessions are all shorter than 3 h is handled: e.g. keep it and use the longest or combined overnight sessions as the outcome, and reserve `no_sleep_data` for missing tracker data. At minimum, report such nights separately in the readout.

### R2-4 — consistency

**Problem**

> State is said to hold 'no sleep values, no derived gaps', but the stored `planned_bedtime` defaults to the median sleep onset of the last 14 nights, which is a derived sleep value. It also contradicts the constraint 'no health values ... in experiment state'.

**Remedy**

> Either accept planned bedtime as a stored derived value and say so in the constraints and state list, or store only a user-confirmed bedtime (the skill proposes the median, the user confirms it).

### R2-5 — completeness

**Problem**

> With one active experiment per user, and lab_create_experiment failing while an experiment is active, there is no way to stop, cancel or abandon a run (illness, lost tracker, a tester quitting). An auto-extended run can last up to 28 nights. A user who wants out is stuck.

**Remedy**

> Add a lab_stop/lab_cancel operation (or an abandon status) and say whether an abandoned run can still be analyzed and how the readout marks early stopping.

### R2-6 — completeness

**Problem**

> The planned_bedtime default needs 14 prior nights of sleep data. A new tester or a newly worn tracker may have few or none, and the behavior in that case is undefined.

**Remedy**

> Specify the fallback: e.g. use the median of the available nights when there are at least N, otherwise require the user to give a planned bedtime (and the skill asks for it).

### R2-7 — completeness

**Problem**

> `travel` (time zone changed by more than 1 hour) is an exclusion code, but lab_flag_night accepts only `user_flag` and `skipped`, and no automatic detection is described. Nothing records a travel exclusion, and 'time zone changed' has no data source (profile time zone? device offset? relative to what baseline?).

**Remedy**

> State how `travel` is set: detected automatically from a named data source compared with the experiment's start time zone, or recorded by the user through lab_flag_night (then add it as a code and subject it to the flag timing rule).

### R2-8 — clarity

**Problem**

> The behavior of lab_analyze before the run is finished is not specified. If it returns interim verdicts, the user can peek and stop or skip nights based on results (optional stopping), which undermines the fixed CI and premise 3.

**Remedy**

> Define lab_analyze during an active run: e.g. it refuses with 'experiment still running' (lab_status shows only counts, never outcomes), or returns an interim result that is clearly labeled and does not change the final verdict rules.

### R2-9 — clarity

**Problem**

> Auto-extension is checked 'on the last scheduled night', but that night's validity is known only after its main sleep has ended and synced the next morning. It is also undefined how an added pair keeps the Friday/Saturday alignment, and when lab_today learns the new nights' arms.

**Remedy**

> Define when the extension check runs (e.g. the first lab_today/lab_status call after the last night's sleep data is available, with a stated sync-delay rule), and state that extension pairs follow the same weekly alignment and seeded arm order.

### R2-10 — clarity

**Problem**

> The rule for asking the eaten-at time ('more than 20 minutes after "now" might apply') is hard to implement: the skill cannot know when the user ate, so it cannot tell whether a log is 20 minutes late. A missed question silently misclassifies adherence.

**Remedy**

> Use a rule the skill can apply: e.g. always confirm the eaten-at time for entries logged after 15:00, with 'now' as the one-tap default, and record the entry at the confirmed time.

### R2-11 — clarity

**Problem**

> An experiment night runs from local noon to the next local noon, but the document does not say which calendar date identifies a night. lab_flag_night(date, ...), the schedule 'date to arm' map, and 'Friday and Saturday' nights all depend on it, and a flag given after midnight is ambiguous.

**Remedy**

> State that a night is identified by the date of its starting noon (so the 'Friday night' starts Friday at 12:00), and that lab_flag_night uses this date.

### R2-12 — feasibility

**Problem**

> 'Last intake' counts caloric drinks over 50 kcal, which needs calorie values on nutrition entries. Chat or photo logs may not carry calories, and the layer-1 spike checks only the eaten-at time, not calories.

**Remedy**

> Either add a spike check that nutrition entries written by the MCP carry calories, or define the fallback (e.g. every drink logged in the window counts unless the user marks it zero-calorie).

### Prior finding evidence

**R1-6 → R2-1 (persisting)**

> Schedule now defines pairs, Fri/Sat weekend and a stored seed, but the algorithm guaranteeing a well-defined balanced schedule for any start_date still fails: pairing consecutive nights with Fri/Sat fixed leaves one unpaired night every week, which only the start-of-run case handles.
